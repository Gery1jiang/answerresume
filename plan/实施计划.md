# Agent 任务拆解系统 — 全量实施计划

## 核心设计理念

**不要将用户整句话分类为单一意图，而是从自然语言中解析出有序的 Action 序列。**

```
用户输入: "抓取产品经理岗位、匹配、新增面试、生成报告"
                           ↓
Action序列: [crawl, match, create_interview, generate_report]
                           ↓
                   模板引擎匹配这个序列
                   ├─ 匹配成功 → 用模板的 DAG（含依赖/参数映射）
                   └─ 匹配失败 → LLM 根据序列生成 DAG
                           ↓
                   DAG校验 → 拓扑调度 → 原子执行 → 结果聚合 → LLM格式化输出
```

好处：
- "抓产品经理并匹配" → `[crawl, match]` → 命中模板
- "抓取A、抓取B、匹配" → `[crawl, crawl, match]` → 命中模板（并行抓取）
- "抓取、匹配、新增面试、生成报告" → `[crawl, match, create_interview, report]` → 无模板 → LLM 拆 DAG
- "解析图片" → `[parse_file]` → 原子任务，不走拆解
- "生成简历" → `[generate_resume]` → 原子任务，不走拆解

## 架构概览

```
用户输入
   ↓
[Action序列解析器]  ← 从自然语言提取有序 Action 列表（每个 Action 映射到一个工具）
   ↓
[是否复合？] ─单→ 保持现有 LangGraph 流程
   │
   └多→ [模板引擎] ← 按 Action 序列模式匹配预定义 DAG 模板
            │
       ├─ 命中 → [模板 DAG] → [校验器] → [调度器] → [原子执行] → [结果聚合]
       │                                                          ↓
       └─ 未命中 → [LLM 拆解器] → [校验器] → [调度器] → [原子执行] → [结果聚合]
                                                                       ↓
                                                            [LLM 格式化最终响应]
```

## Phase 1：数据结构定义（`services/task/models.py`）

### 核心模型

#### Action — 原子操作（最小单元）
```python
@dataclass
class Action:
    action_id: str
    tool: str                       # 工具名，如 "kimi_crawl_tool"
    input_params: dict              # 入参
    output_key: str                 # 结果存入的键名（供下游引用）
    retry: int = 1
    timeout: int = 120
    depends_on: list[str] = field(default_factory=list)  # 依赖的 action_id 列表
```

#### SubTask — 子任务（可包含多个 Action）
```python
@dataclass
class SubTask:
    sub_task_id: str
    goal: str                       # 子目标描述
    actions: list[Action]
    depend_on: list[str] = field(default_factory=list)  # 依赖的子任务ID
    priority: int = 0
```

#### TaskDAG — DAG 结构
```python
@dataclass
class TaskDAG:
    nodes: dict[str, SubTask]
    edges: list[tuple[str, str]]    # (from_id, to_id)
```

#### TaskRoot — 根任务
```python
@dataclass
class TaskRoot:
    task_id: str
    goal: str                       # 原始目标的标准化描述
    action_sequence: list[dict]     # 原始 Action 序列 [{tool, params}, ...]
    dag: TaskDAG
    error_strategy: str = "continue"
```

### 验收标准
- 可实例化所有模型
- `Action(tool="kimi_crawl_tool", ...)` 的 tool 在 `tool_meta.TOOL_METADATA` 中可查到
- 可序列化为 dict（用于日志/存储）

## Phase 2：Action 序列解析器（`services/task/action_parser.py`）

### 核心函数

```python
def parse_actions(user_input: str) -> list[dict]:
    """从自然语言中提取有序的 Action 序列

    输入: "帮我抓取杭州的产品经理岗位并匹配"
    输出: [
        {"tool": "kimi_crawl_tool", "params": {"keywords": "产品经理", "city": "杭州"}},
        {"tool": "match_jobs_tool", "params": {}},
    ]

    输入: "抓取岗位、匹配、新增面试、生成报告"
    输出: [
        {"tool": "kimi_crawl_tool", "params": {}},
        {"tool": "match_jobs_tool", "params": {}},
        {"tool": "create_interview_record_tool", "params": {}},
        {"tool": "generate_interview_report_tool", "params": {}},
    ]
    """
```

### 实现策略

#### 第一层：关键词断句
将用户输入按标点/连接词拆分为子句：
```python
_SEPARATORS = r"[，。、；\n]|并|然后|再|接着|之后|且|还有|同时"
```
拆分后得到若干子句：
```
["抓取杭州的产品经理岗位", "匹配", "新增面试", "生成报告"]
```

#### 第二层：每个子句 → Action
对每个子句，用关键词匹配判定操作类型，同时提取参数：

| 关键词 | Action tool | 提取参数 |
|--------|-------------|---------|
| 抓取/爬取/搜索 岗位 | kimi_crawl_tool | keywords, city, platform |
| 匹配/评分/评估 岗位 | match_jobs_tool | job_ids（留空待上游填充） |
| 新增/创建 面试 | create_interview_record_tool | company, job_title, ... |
| 生成 报告/面试宝典 | generate_interview_report_tool | company, job_title |
| 解析 文件 | parse_file_tool | filename |
| 生成 简历 | generate_resume_tool | target_job |
| 查询 数据/信息 | query_system_data_tool | type |

#### 第三层：原地提取参数
```python
def _extract_params(text: str) -> dict:
    """从文本中提取结构化参数"""
    params = {}
    # 城市提取
    city_match = re.search(r"(北京|上海|广州|深圳|杭州|成都|武汉|南京|苏州)", text)
    if city_match: params["city"] = city_match.group(1)
    # 关键词提取
    # 删掉已知动词/城市后剩下的名词
    ...
    return params
```

#### 兜底：单 Action 判断
如果关键词断句没有拆分（即没有连接词），但整体匹配某个工具：
```python
def _try_single_action(text: str) -> list[dict] | None:
    """尝试将整句匹配为单 Action"""
```

### 多 Action 的 Action 序列处理

如果解析结果有多个相同的动作（如 `[crawl, crawl, match]`）：
- 保留所有动作，不合并
- 模板引擎可以识别可并行处理的相同动作

### 验收标准
- `parse_actions("抓取杭州产品经理岗位")` → `[{tool: "kimi_crawl_tool", params: {keywords: "产品经理", city: "杭州"}}]`
- `parse_actions("抓取岗位、匹配、新增面试、生成报告")` → 4 个 Action 的列表
- `parse_actions("解析这张图片")` → `[{tool: "parse_file_tool", params: {}}]`
- `parse_actions("你好")` → `[]`（无操作，纯对话）
- 原有文件上传标记 `[文件: xxx]` 兼容处理

## Phase 3：模板引擎（`services/task/templates.py`）

### 模板定义方式

每个模板注册时包含：
1. **模式匹配函数**：`matches(sequence: list[dict]) -> bool` — 判断 Action 序列是否匹配
2. **DAG 生成函数**：`build(sequence, params) -> TaskRoot` — 按 Action 序列生成完整的 DAG

```python
@dataclass
class TaskTemplate:
    name: str
    description: str
    matches: Callable[[list[dict]], bool]       # 序列模式匹配
    build: Callable[[list[dict]], TaskRoot]      # 生成 DAG
```

### 模板注册表

```python
TASK_TEMPLATES: list[TaskTemplate] = []
```

### 模板1：crawl_and_match — 抓取后匹配
```python
def _match_crawl_and_match(seq: list[dict]) -> bool:
    """匹配 [crawl, ...crawl?, match] 模式"""
    if len(seq) < 2: return False
    # 最后一个必须是 match，前面都是 crawl
    return seq[-1]["tool"] == "match_jobs_tool" and all(
        s["tool"] == "kimi_crawl_tool" for s in seq[:-1]
    )

def _build_crawl_and_match(seq: list[dict]) -> TaskRoot:
    """
    DAG:
        crawl_1 ──┐
        crawl_2 ──┤──→ match (等待所有 crawl 完成)
                   ...
    """
    actions = []
    for i, s in enumerate(seq[:-1]):  # 所有抓取
        actions.append(Action(
            action_id=f"crawl_{i}",
            tool="kimi_crawl_tool",
            input_params=s["params"],
            output_key=f"crawl_result_{i}",
        ))
    # 汇总 job_ids 给 match
    match_action = Action(
        action_id="match",
        tool="match_jobs_tool",
        input_params={},  # job_ids 在调度时从上游结果填充
        output_key="match_result",
        depends_on=[a.action_id for a in actions],
    )
    ...
```

### 序列匹配逻辑

```python
def match_template(sequence: list[dict]) -> TaskTemplate | None:
    """按顺序依次匹配，返回第一个匹配的模板"""
    for tmpl in TASK_TEMPLATES:
        if tmpl.matches(sequence):
            return tmpl
    return None
```

### 验收标准
- `match_template([{tool:"kimi_crawl_tool"}, {tool:"match_jobs_tool"}])` → crawl_and_match 模板
- `match_template([{tool:"kimi_crawl_tool"}, {tool:"kimi_crawl_tool"}, {tool:"match_jobs_tool"}])` → crawl_and_match 模板（多 crawl 并行）
- `match_template([{tool:"parse_file_tool"}, {tool:"create_interview_record_tool"}])` → parse_then_create_interview 模板
- `match_template([{tool:"generate_resume_tool"}])` → None（单 Action，不走拆解）

## Phase 4：校验器（`services/task/validator.py`）

同时支持 **DAG 校验** 和 **单 Action 校验**，覆盖两种执行路径。

### 单 Action 校验（原子任务用）

```python
def validate_action(tool: str, params: dict) -> list[str]:
    """校验单个工具调用的合法性"""
```

1. **工具存在性** — tool 必须在 `tool_meta.TOOL_METADATA` 中存在
2. **必需参数完整性** — 对照 `ToolMeta.parameters` 中 `required=True` 的参数是否都在 params 中
3. 返回错误列表，空=通过

### DAG 校验（复合任务用）

```python
def validate_dag(root: TaskRoot) -> list[str]:
    """返回错误列表，空=通过"""
```

1. **工具存在性** — 每个 Action 的 tool 必须在 `tool_meta.TOOL_METADATA` 中存在
2. **循环依赖** — 拓扑排序检测环
3. **必需参数完整性** — 对照 `ToolMeta.parameters` 检查 required 参数
4. **依赖有效性** — `depends_on` 引用的 action_id 全都在 DAG 中
5. **原子性** — 每个 Action 的 tool 必须是单一工具名

### 集成点

- `validate_action` 在 `_gateway_tool_node` 中调用 → 在 `_gateway.call_sync_to_text()` 之前校验
- `validate_dag` 在 DAG 调度器执行前调用

### 验收标准
- `validate_action("kimi_crawl_tool", {})` → `["缺少必需参数: keywords"]`
- `validate_action("nonexistent_tool", {})` → `["工具 nonexistent_tool 不存在"]`
- `validate_action("kimi_crawl_tool", {keywords: "产品经理"})` → `[]`
- `validate_dag(合法TaskRoot)` → `[]`
- `validate_dag(含不存在工具的TaskRoot)` → `["工具 xxx 不存在"]`
- `validate_dag(含环)` → `["检测到循环依赖: ..."]`

## Phase 5：DAG 调度器（`services/task/scheduler.py`）

### 核心功能

```python
class DAGScheduler:
    def __init__(self, gateway: ToolGateway):
        self.gateway = gateway

    def execute(self, root: TaskRoot, context: dict) -> dict:
        """执行整个 DAG，按拓扑顺序调度

        返回: {"action_id": result, ...}
        """
```

### 拓扑排序

```python
def topological_sort(dag: TaskDAG) -> list[list[str]]:
    """返回分层列表，每层内的 Action 可并行

    例: [["crawl_0", "crawl_1"], ["match"]]
    """
```

### 执行流程

1. 按分层逐层执行
2. 同一层内用 `ThreadPoolExecutor` 并行
3. 每个 Action：
   - 检查缓存 → 命中直接返回
   - 通过 `ToolGateway.call_sync_to_text()` 执行
   - 异常处理：按 `error_strategy` 决定跳过/中断
   - 结果存入 `action_results[output_key]`
4. 跨 Action 数据传递：`$output_key` 语法自动填充下游参数
   - 如 match 的 `job_ids` 自动从 `$crawl_0.job_ids` 填充

### 中间结果注入

当 Action B 依赖 Action A 时：
- Action B 的 `input_params` 中的 `$output_key` 占位符在执行前替换为 A 的实际结果值

## Phase 6：拆解引擎（`services/task/engine.py`）

### 引擎类

```python
class TaskDecompositionEngine:
    """双引擎拆解"""

    def should_decompose(self, actions: list[dict]) -> bool:
        """判断是否需要走拆解"""
        return len(actions) >= 2    # 2+ 个 Action 走拆解

    def decompose(self, actions: list[dict], user_input: str) -> TaskRoot | None:
        """分解 Action 序列为 DAG"""
        # 1. 尝试模板匹配
        tmpl = match_template(actions)
        if tmpl:
            return tmpl.build(actions)

        # 2. 模板未命中 → LLM 动态拆解
        return self._llm_decompose(actions, user_input)

    def _llm_decompose(self, actions: list[dict], user_input: str) -> TaskRoot:
        """LLM 将 Action 序列转化为 DAG（含依赖关系）"""
```

### 流程整合

```
用户输入
   ↓
parse_actions() → Action 序列
   ↓
should_decompose() → False → 走现有 LangGraph 流程
   ↓ True
match_template() → 命中 → 模板.build() → TaskRoot
   ↓ 未命中
LLM 动态拆解 → TaskRoot
   ↓
validator.validate() → 通过 → scheduler.execute()
   ↓ 不通过
返回错误给用户
```

## Phase 8：集成到 Agent Service（`services/agent_service.py`）

### 改造点

#### 1. 在 `stream_agent_events` / `run_agent` 入口处新增拆解逻辑

在 LangGraph invoke 之前：
```python
# 伪代码
actions = parse_actions(user_message)
if len(actions) >= 2:
    engine = TaskDecompositionEngine()
    root = engine.decompose(actions, user_message)
    if root:
        errors = validate(root)
        if errors:
            yield error  # 校验不通过
            return
        scheduler = DAGScheduler(_gateway)
        results = scheduler.execute(root, ctx)
        # 将执行结果注入到消息中，让 LLM 只负责格式化输出
        prompt = f"以下是工具执行结果，请用自然语言回复用户：\n{results}"
        # 走 LLM 生成最终回复
```

#### 2. 修改 `_gateway_tool_node` — 原子任务也走校验

在 `_gateway.call_sync_to_text()` 之前调用 `validate_action()`：
```python
# _gateway_tool_node 中，执行前
errors = validate_action(tool_name, tool_args)
if errors:
    msg = f"工具调用校验不通过: {'; '.join(errors)}"
    new_messages.append(ToolMessage(content=msg, ...))
    continue
```

#### 3. 保留原子任务走原有 LangGraph

当 `len(actions) < 2` 时，走现有 LangGraph 流程，但 `_gateway_tool_node` 新增了校验。

#### 4. DAG 执行中的事件推送

`scheduler.execute()` 内部调用 `_push_live_event`：
- `{"type": "dag_plan", "data": dag_structure}` 开始
- `{"type": "dag_progress", "data": {"action_id": "...", "status": "running|done|failed"}}` 每步
- `{"type": "tool_call", "data": ...}` 每个 Action 调用时
- `{"type": "tool_result", "data": ...}` 每个 Action 返回时
