## 二、根本问题

### 2.1 分层缺失：平铺式架构

没有 `controller → service → repository` 分层，所有模块都是平铺的：
- router 里直接写 DB 查询（`admin.py:317` 直接 `db.query(CrawledJob)`）
- service 里直接读写数据库、直接调其他 service
- 任何改动都可能波及无关模块

### 2.2 无接口抽象

- 没有 `BaseRepository` / `BaseService` 接口
- 依赖是具体实现（`from services.jd_matcher import match_jd`），不是接口
- 无法替换实现，测试困难

### 2.3 全局可变状态

```
config.py: settings = Settings()  # 全局单例
main.py:    settings.ADMIN_API_KEY = cfg["llm_api_key"]  # 运行时修改
agent_service.py: llm_with_tools = None  # 全局缓存，不随配置更新
```

运行时修改全局 `settings` 对象，多 worker 下行为不可预测。

### 2.4 多层配置源混合

配置来自三个地方：
```python
# 1. .env 文件（启动时加载）
ADMIN_API_KEY: str = ""

# 2. 数据库 app_config 表（lifespan 时覆盖 settings）
settings.ADMIN_API_KEY = cfg["llm_api_key"]

# 3. 硬编码默认值
ADMIN_LLM_MODEL: str = "LongCat-2.0-Preview"
```

改配置要改三个地方，不知道谁优先。

### 2.5 文件解析链路无隔离

```
agent_upload → 存到 uploads/<uuid>.png
_chat → _apply_file_context → [文件: uuid.png]
parse_file_tool → _resolve_and_parse → 搜索 uploads/{uid}/, uploads/, 所有子目录
```

文件查找有 fallback 链，不同用户的同名文件可能互相干扰。

### 2.6 单体 Docker 容器

- backend 容器里包含了所有服务：Agent、RAG、爬虫、文件解析、简历生成
- 一个模块 OOM 拖垮整个后端
- 无法独立扩缩容

### 2.7 无测试策略

- `tests/` 目录存在但无实际测试
- 改一行代码不知道波及范围
- 依赖图分析只能靠人工

### 2.8 前端无状态层

- React 组件直接调用 API，没有中间状态管理层
- 页面间共享状态靠重复请求

## 三、改进方案

### 3.1 分层架构（Phase 1 - 核心）

```
┌─────────────────────────────────────────────────────┐
│  Router (路由层)                                     │
│  - 参数校验, 权限控制, 请求响应转换                   │
│  - 不包含业务逻辑, 不直接查 DB                        │
├─────────────────────────────────────────────────────┤
│  Service (服务层)                                    │
│  - 业务逻辑, 事务边界                                 │
│  - 只能调用 Repository 和其他 Service 的接口          │
│  - 不直接依赖具体实现                                 │
├─────────────────────────────────────────────────────┤
│  Repository (数据层)                                 │
│  - 数据库读写, ORM 查询                              │
│  - 不包含业务逻辑                                    │
│  - 每张表一个 Repository                             │
├─────────────────────────────────────────────────────┤
│  Model (模型层)                                      │
│  - ORM 定义                                          │
│  - 纯数据, 无逻辑                                    │
└─────────────────────────────────────────────────────┘
```

#### 3.1.1 Repository 模式


```python
# base.py
from abc import ABC, abstractmethod
from sqlalchemy.orm import Session

class BaseRepository[T](ABC):
    def __init__(self, db: Session):
        self.db = db

    @abstractmethod
    def get_model(self) -> type[T]: ...

    def get_by_id(self, id: str) -> T | None:
        return self.db.get(self.get_model(), id)

    def list(self, **filters) -> list[T]: ...
    def create(self, **data) -> T: ...
    def update(self, id: str, **data) -> T | None: ...
    def delete(self, id: str) -> bool: ...
```

### 3.2 依赖注入（Phase 1）

```python
# services/container.py
from functools import lru_cache

class ServiceContainer:
    def __init__(self, db_session_factory):
        self._db = db_session_factory
        self._services = {}

    @property
    def file_service(self) -> FileService:
        if "file" not in self._services:
            self._services["file"] = FileServiceImpl(self._db)
        return self._services["file"]

    @property
    def job_service(self) -> JobService:
        if "job" not in self._services:
            self._services["job"] = JobServiceImpl(
                self._db,
                self.file_service,    # 显式依赖
            )
        return self._services["job"]

container = ServiceContainer(lambda: SessionLocal())
```

### 3.5 事件系统（Phase 2）

```python
# core/events.py
from enum import Enum
from dataclasses import dataclass

class EventType(Enum):
    FILE_UPLOADED = "file.uploaded"
    JOB_CRAWLED = "job.crawled"
    JOB_MATCHED = "job.matched"
    RESUME_GENERATED = "resume.generated"

@dataclass
class Event:
    type: EventType
    data: dict
    user_id: str

class EventBus:
    _handlers: dict[EventType, list[callable]] = {}

    @classmethod
    def on(cls, event_type: EventType):
        def decorator(fn):
            cls._handlers.setdefault(event_type, []).append(fn)
            return fn
        return decorator

    @classmethod
    def emit(cls, event: Event):
        for handler in cls._handlers.get(event.type, []):
            handler(event)
```

使用：
```python
@EventBus.on(EventType.FILE_UPLOADED)
def on_file_uploaded(event: Event):
    """文件上传后自动触发解析（异步）。"""
    parse_task.delay(event.data["file_id"])
```

### Phase 1.5 代码迁移策略（修正：2026-06-25）

**问题发现**：admin.py (2262行) 和 visitor.py (630行) 对 DB 和旧 Service 高度耦合，逐端点替换风险高且收益边际递减。

**修正策略**：按价值/风险分批迁移

| 批次 | 目标 | 风险 | 价值 |
|------|------|------|------|
| A | 工具函数 + 配置端点（_load_config/_save_config + stats/UserConfig） | 低 | 高 |
| B | visitor.py 全部（630行，模式统一） | 中 | 高 |
| C | admin.py interview-guide/jobs 端点中可用 repo 替换的部分 | 中 | 中 |
| D | admin.py 剩余端点 + 旧 Service 调用 | 高 | 低 |

**分批原则**：
- 批次 A/B 在本轮完成
- 批次 C 在批次 B 通过测试后进行
- 批次 D 延后到 Phase 2（与事件系统/Service 接口化协同）
- 旧 Service 类（interview_guide_service/resume_service 等）保留不动，只将 DB 查询部分抽到 repo

**核心判断**：admin.py 中大部分端点调用旧 Service 类（含复杂业务逻辑如 commute 计算、JD 匹配、向量库重建等），强行替换为 repo 会导致逻辑丢失。Repository 模式的主要收益在 agent_service.py 等直接使用 db.query 的地方已体现。

## 六、风险控制

1. **逐步替换** — 旧路由和新代码并存，不一次全部重写
2. **保持 API 不变** — Router 接口签名不改，前端不受影响
3. **每次重构提交一次** — git commit 粒度明确，可回退
4. **先加测试再加重构** — 每个 Repository 写单元测试后再迁移
