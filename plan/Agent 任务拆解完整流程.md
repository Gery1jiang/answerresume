# Agent 任务拆解完整流程 + 工程化落地方案
## 一、Agent 标准任务拆解完整流程（通用分层流程）
### 阶段1：任务输入校验与意图归一化
1. **原始任务接收**：用户自然语言/上游系统结构化指令输入
2. **合法性校验**
   - 权限校验：Agent 是否具备执行该任务权限（RBAC 绑定工具、数据）
   - 风险校验：敏感操作、资源超限、循环风险、违规指令拦截
   - 格式校验：结构化参数缺失、歧义、模糊输入标记
3. **意图标准化**
   LLM 输出统一结构化任务描述：目标、约束、输出格式、截止条件、资源限制
> 输出产物：标准化 Task Root（根任务结构体）

### 阶段2：根任务可拆分判定（核心分支）
用规则+LLM 双判断：
1. **原子任务**：无需拆分、单一工具单次调用可完成 → 直接进入执行调度
2. **复合任务**：多步骤、多工具、多依赖、多子目标 → 进入分层拆解链路

### 阶段3：分层递归拆解（自上而下拆解树生成）
采用 **目标-条件-动作** 三层拆解范式
1. **第一层：拆分顶层子目标**
   把总任务拆成多个并行/串行独立子目标，子目标之间标记依赖关系（DAG 依赖图）
2. **第二层：每个子目标拆成执行步骤**
   每个子目标拆解成有序操作步骤，明确前置依赖、输入输出
3. **第三层：步骤下沉为原子Action**
   最小不可拆分单元 = Action，每个 Action 绑定单一工具/函数调用，包含：
   - 工具ID、入参模板、失败重试策略、超时、校验规则
> 输出产物：**任务DAG树 / 任务拆解AST**，记录父子关系、依赖、优先级

### 阶段4：依赖拓扑排序与任务分组
1. 提取所有 Action 依赖关系，构建有向无环图
2. 拓扑排序区分：串行任务链、可并行任务组
3. 资源分组：按工具类型、算力、API 配额分组调度

### 阶段5：子任务边界约束与容错配置
给每个子Action注入工程控制参数：
- 重试次数、超时阈值、失败降级策略（跳过/回滚/告警）
- 中间结果缓存、断点续跑标识
- 输出校验规则（正则、JSON Schema、数值阈值）

### 阶段6：调度执行 & 中间结果回灌修正
1. 按拓扑顺序分发子任务给执行Worker
2. 每一步执行完成后，校验输出是否满足子目标验收标准
3. **动态重拆解（闭环修正）**
   子任务结果不达标、出现新信息、目标变更时，重新触发局部拆解，更新DAG，而非全量重跑

### 阶段7：任务合并、结果聚合 & 收尾
1. 收集所有叶子Action输出，按根任务要求聚合、格式化
2. 资源回收、日志落盘、任务树持久化、指标上报

## 二、工程化落地方法（可直接落地的架构与规范）
### 1. 数据结构标准化：定义统一任务拆解Schema
所有拆解输出强制结构化，杜绝纯文本，推荐JSON Schema规范
```json
{
  "task_id": "root-xxx",
  "task_type": "compound/atomic",
  "goal": "顶层目标",
  "constraints": ["时间限制", "数据范围", "权限"],
  "dag": {
    "nodes": [子任务节点],
    "edges": [依赖关系 u->v]
  },
  "sub_tasks": [
    {
      "sub_task_id": "sub-1",
      "depend_on": ["sub-0"],
      "priority": 1,
      "actions": [
        {
          "action_id": "act-01",
          "tool": "tool_search",
          "input_schema": {},
          "output_check": "JSON_SCHEMA_ID",
          "retry": 2,
          "timeout": 10000
        }
      ],
      "accept_condition": "子任务完成校验表达式"
    }
  ],
  "aggregator": "结果聚合函数ID",
  "error_strategy": "continue/rollback/abort"
}
```
工程收益：可序列化存储、可入库、可前后端渲染任务流程图、可程序自动解析调度。

### 2. 双引擎拆解架构（规则引擎 + LLM 分层拆解，降低成本）
#### （1）硬规则层（优先执行，减少LLM调用）
- 预设常见任务模板：报表生成、数据查询、文件处理、API批量调用
- 固定拆分逻辑、固定DAG，匹配模板直接生成任务树，零LLM消耗
- 基于工具能力图谱匹配：系统维护 `ToolCapabilityMap`，明确每个工具能做/不能做，自动切分边界

#### （2）LLM 通用拆解层（无匹配模板时启用）
强制LLM输出结构化DAG，增加Prompt约束：
1. 先判断是否可拆分；
2. 输出子目标、依赖顺序；
3. 每个步骤必须映射到现有工具，禁止生成不存在工具；
4. 自动识别并行/串行分支；
5. 输出校验条件、失败处理方式。

#### （3）校验层（LLM输出后强制校验）
程序自动校验LLM输出的任务树合法性：
- 工具是否存在
- 依赖是否循环（DAG校验，无环）
- 参数是否完整
- 子目标是否覆盖原始总任务，无遗漏、无多余步骤

### 3. DAG 任务调度引擎（核心工程载体）
拆解后的任务树统一由DAG调度器执行，能力：
1. 拓扑排序自动分发并行子任务，提升吞吐
2. 断点续执行：每个Action执行结果持久化，崩溃后从成功节点继续
3. 子任务独立超时、熔断：单个工具失败不阻塞整个任务流
4. 资源隔离：多Agent任务资源配额隔离，防止抢占

### 4. 分层缓存机制，优化重复拆解开销
1. **任务模板缓存**：相同意图标准化任务命中缓存，直接复用DAG，无需重复拆解
2. **中间Action结果缓存**：相同入参工具调用缓存返回，减少重复调用
3. **拆解元数据持久化**：任务全链路树存入数据库，支持回放、调试、审计

### 5. 动态迭代闭环：执行反馈反向优化拆解逻辑
工程化闭环设计：
1. 记录拆解失败案例：LLM拆分不合理、依赖错误、步骤缺失
2. 定期样本回流微调Prompt/扩充规则模板
3. 监控指标：拆解准确率、冗余Action占比、重拆解次数，迭代优化拆分逻辑

### 6. 可观测与运维体系（工程必备）
- 拆解链路日志：根任务→子任务→Action全链路ID追踪
- 指标埋点：拆解耗时、LLM调用量、拆分错误率、动态重拆解次数
- 可视化面板：渲染任务DAG流程图，直观查看拆分结构、执行状态
- 审计日志：所有拆解步骤、LLM输出、修改记录持久留存

## 三、两种主流工程化拆解模式选型
### 模式A：静态模板拆解（高并发、标准化业务首选）
适用：固定业务流程Agent（数据ETL、报表、工单处理）
流程：任务匹配模板 → 直接加载预定义DAG → 填充参数执行
优势：速度快、成本低、稳定性高、可控性强

### 模式B：LLM动态递归拆解（通用开放式Agent）
适用：通用对话Agent、复杂未知任务、多工具组合场景
流程：输入→校验→LLM拆DAG→程序校验DAG→拓扑调度→执行校验→动态修正
优势：适配任意自然语言任务，灵活；缺点：LLM开销高，需配套校验机制

## 四、落地避坑工程规范
1. **禁止无限递归拆解**：设置最大分层深度（如最多5层子任务），防止LLM无限细分
2. **原子Action最小化**：一个Action只做一件事，不允许一个Action包含多工具调用
3. **依赖严格DAG**：检测循环依赖直接报错，避免死锁
4. **分离拆解与执行**：拆解模块、调度模块、工具执行模块解耦，可独立迭代
5. **输出强校验**：每个子任务必须设置验收条件，不达标则触发局部重拆，避免无效执行

## 五、极简落地架构分层
```
用户输入层
    ↓
意图归一化&校验层（规则拦截）
    ↓
任务拆解层
    ├─ 模板匹配引擎（静态DAG）
    └─ LLM动态拆解引擎（输出结构化DAG）
    ↓
DAG校验器（去环、工具校验、参数校验）
    ↓
拓扑调度引擎（并行/串行分发）
    ↓
Action执行Worker（工具调用、重试、超时）
    ↓
结果校验 + 动态重拆解闭环
    ↓
结果聚合输出层
```
