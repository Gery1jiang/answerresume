# 自动求职模块设计方案

## 一、概述

在现有岗位雷达基础上，增加一个一级「自动求职」模块，通过 Kimi WebBridge 操作真实浏览器，模拟真人浏览招聘平台、自动打招呼、聊天沟通、投递简历、约定面试，并记录全过程。

---

## 二、WebBridge 可行性分析

| 动作 | WebBridge 方案 | 风险 | 缓解措施 |
|------|---------------|------|---------|
| 打开岗位详情 | `navigate` | 低 | — |
| 点击「打招呼」 | `click` | 低 | 按钮通常不检查 `isTrusted` |
| 读聊天记录 | `snapshot` → 提取 a11y tree | 低 | — |
| 输入聊天消息 | `fill` on `<textarea>`/`[contenteditable]` | 中 | 可退到 `evaluate` 触发平台内部 API |
| 发送消息 | `click` 发送按钮 | **高** | 按钮可能检查 `isTrusted`；退路：`evaluate` 调平台 Ajax 接口直发 |
| 接收对方消息 | 轮询 `snapshot` / `evaluate` 读 DOM | 中 | 需要频率控制，防风控 |
| 投递简历 | `click` + `upload` | 中 | upload 支持 `<input type=file>` |
| 约定面试 | `fill` 日期/备注 + `click` 提交 | 中 | date picker 可能需额外处理 |
| 验证码 | — | **高** | WebBridge 无法自动过验证码；需暂停 + 通知用户手动处理 |
| 检测岗位列表变化 | `snapshot`/`evaluate` → 对比 jobId 集合 | 低 | — |

**结论**：WebBridge **基本可行**。聊天发送消息是最大风险点，若 `isTrusted` 阻止，通过 `evaluate` 调平台原生 XHR/fetch 可绕过（浏览器已登录，cookie/session 有效）。

### 引擎生命周期

```
前端点击「启动引擎」
  → POST /auto-job/engine/start
  → 后端创建 asyncio.Task
  → 引擎进入监控循环

前端点击「停止引擎」
  → POST /auto-job/engine/stop
  → 后端 cancel() Task
  → 引擎清理 (close_session)

前端 GET /auto-job/engine/status
  → 返回 {running, uptime, today_found, today_chatted, ...}
```

## 四、双模式流程

### 模式 A：列表监控模式

WebBridge 打开招聘平台搜索页，定时检测岗位列表变化。

```
引擎启动
  │
  ├─ navigate → BOSS/51job 搜索页 (关键词+城市)
  │
  ├─ 循环 (每 N 分钟):
  │   ├─ scroll + evaluate(CARD_JS) → 当前页所有岗位
  │   ├─ 提取 {jobId, title, company, salary, url, ...} 集合
  │   │
  │   ├─ 新出现 (current_ids - known_ids)
  │   │   └─ 匹配度 ≥ 阈值 → 自动创建任务 → 进入模式 B
  │   │
  │   ├─ 消失 (known_ids - current_ids)
  │   │   └─ 对应任务 → status = expired
  │   │
  │   └─ 更新 known_ids → 持久化
  │
  └─ 引擎停止 / 任务异常
```

### 模式 B：单岗位求职模式

每个岗位独立的状态机推进。

```
状态机:
  NEW → CHATTING → APPLIED → INTERVIEW_DONE
    ↘               ↘          ↘
     REJECTED     EXPIRED    STOPPED

NEW:
  navigate 到岗位详情页
  → click "打招呼"/"立即沟通"
  → snapshot 确认聊天面板弹出
  → status = CHATTING

CHATTING (循环):
  ├─ snapshot 读聊天面板最新消息
  ├─ HR有新消息 → 存chat_log
  │   └─ 调 agent 生成回复
  │       (context = JD + 简历 + 历史 + HR消息)
  │   └─ fill 输入框 + click 发送
  │   └─ 随机等待 30-120s
  ├─ 识别到约面意图 → 创建面试记录 → status = INTERVIEW_DONE
  ├─ 识别到拒绝 → status = REJECTED
  ├─ 识别到下架 → status = EXPIRED
  ├─ 24h无回复 → follow-up 一次
  └─ 48h无回复 → status = STOPPED

APPLIED:
  已投递简历后继续对话等待反馈

INTERVIEW_DONE → 收录到面试宝典 → 任务完成
```

## 六、对话管理器（复用访客端 Agent）

```
HR 消息
  │
  ▼
chat_manager.py:
  1. snapshot 读聊天面板 → 提取最新消息
  2. 构造 context:
     {
       "jd": jd_text,
       "resume": user_resume,
       "company": company_info,
       "history": [...最近10轮chat_log...],
       "hr_message": "你好，可以看看简历吗？",
       "stage": "chatting"  // 当前求职阶段
     }
  3. POST /agent/chat → LLM 生成回复
  4. WebBridge fill + click 发送
  5. 检查回复中有无约面/拒绝意图
  6. 随机等待 → 继续轮询
```

访客端 agent 已经具备：
- 知识库/简历访问
- LLM 对话生成
- 会话上下文管理
- 身份伪装（求职者身份）

对话管理器只需要写胶水层（读聊天面板 → 构造 context → 调 agent → 发消息）。

## 九、风险与边界

| 风险 | 影响 | 应对 |
|------|------|------|
| `isTrusted=false` 发不出消息 | 对话卡死 | 退到平台 HTTP API 直发（浏览器已登录，cookie 有效） |
| 验证码/滑块 | 全流程卡住 | snapshot 检测 → 通知用户手动处理 → 继续 |
| 平台风控封号 | 账号不可用 | 慢速(真实间隔)、随机化、限制日活(每平台≤50次/天) |
| HR 不回复 | 任务搁置 | 24h 后自动 follow-up 一次，48h 无回复标为静默 |
| 平台改版 selector 失效 | 提取失败 | 优先使用 snapshot @e 语义选择器，定期维护 |
| LLM 回复不合适 | 引起 HR 反感 | 内置回复模板 + 审核规则；支持用户手动覆写 |
| 多任务并发 | 浏览器 tab 爆炸 | 每次只处理 1 个活跃任务，其余排队 |

## 十、实现优先级

| 优先级 | 内容 | 说明 |
|--------|------|------|
| **P0** | 模式 B：详情页打招呼 + 基础对话循环 | 快验证可行性（一个岗位从打开到聊几轮） |
| **P0** | 面试宝典 CRUD | 约面后可手动/自动录入 |
| **P1** | 模式 A：列表监控 + 新岗位检测 | 自动发现新岗位并进入模式 B |
| **P1** | 引擎启停控制 + 前端面板 | 启动/停止/状态 |
| **P1** | 被动打招呼（HR 先发消息检测） | 引擎轮询时也能发现已有对话 |
| **P2** | 发送降级（isTrusted 失败时走 API） | 提升消息发送成功率 |
| **P2** | 风控：随机延时 / 日限量 / 验证码检测 | 防封号 |
| **P3** | 多平台并行 | BOSS + 51job + 智联同时监控 |
| **P3** | 统计看板 / 日历视图 | 可视化 |
